# LoctekMotion (TekDesk 2.0) — Serial Protocol

Reverse-engineered wire protocol for the **CB38M2A-1** control box / **HS01B-1**
keypad, verified against the physical desk and cross-checked against prior
community research (see [References](#references)).

## Frame format

The keypad bus is **9600-baud 8N1 UART**. Every frame is:

```
9B <len> <type> <payload...> <crc16> 9D
```

- `9B` start byte, `9D` end byte.
- `<len>` = number of bytes from `<len>` to `9D` inclusive (i.e. `type + payload + crc + end`).
- `<type>` = message class (constant per class).
- `<crc16>` = CRC16/MODBUS (poly `0xA001`, init `0xFFFF`) over `len + type + payload`, transmitted **high byte first**.

### Message types

| Type | Direction | Meaning |
|------|-----------|---------|
| `0x02` | keypad -> control box | button command (2-byte payload) |
| `0x12` | control box -> keypad | height / 7-segment display frame |
| `0x11` | control box -> keypad | status/heartbeat frame (payload `0x7C`) |
| `0x15` | control box -> keypad | status/heartbeat frame (payload `0xBF`) |
| `0x13` | control box -> keypad | referenced upstream; **never observed** on this box, including during motor travel |

## Button commands (type `0x02`)

The payload is **two bytes**. Each physical key sets one bit in the **first**
payload byte. Held key combinations OR their bits into a single frame — verified
live to full generality, including a **three-key** combo (`0x61` = A+M+Up).

### Single keys

| Payload | Bit | Function |
|---------|-----|----------|
| `00 00` | —      | **Wake** / heartbeat (idle frames) |
| `01 00` | `0x01` | **Up** (raw motor while held; also increments a value *only while the alarm menu is in edit mode*) |
| `02 00` | `0x02` | **Down** (raw motor; decrements a menu value only in edit mode) |
| `04 00` | `0x04` | Memory preset **M1** |
| `08 00` | `0x08` | Memory preset **M2** |
| `10 00` | `0x10` | Memory preset **M3** (stand) |
| `20 00` | `0x20` | **M** — Memory/Set (program a preset) |
| `40 00` | `0x40` | **A** — Alarm: short tap = enter set-mode / confirm; **long hold (~4 s) = alarm OFF** (this panel variant only; not in the reference tables) |
| `00 01` | byte-2 `0x01` | **Preset 4 (sit)** — documented upstream, no physical key on this 7-key panel; the control box still accepts it. **Not exercised on this desk.** |

### Combinations (bitmask OR)

Verified live. The bit-OR model holds for every subset of keys:

| Payload | Keys | Desk response |
|---------|------|---------------|
| `03 00` | Up + Down | no dedicated function observed |
| `05 00` | M1 + Up | no-op |
| `0C 00` | M1 + M2 | no-op (preset combos ignored) |
| `14 00` | M1 + M3 | no-op |
| `18 00` | M2 + M3 | no-op |
| `24 00` | M + M1 | no-op |
| `28 00` | M + M2 | no-op |
| `30 00` | M + M3 | no-op |
| `41 00` | A + Up | alarm menu (A bit dominates) |
| `60 00` | **A + M** | enters a **settings/parameter display** showing `012` — see below |
| `61 00` | A + M + Up | alarm/settings menu (A bit dominates) |

**Key findings:**

- **Preset and memory combinations are no-ops.** The control box acts only on
  single functional keys, never on preset/memory *combinations*.
- **The `A` (`0x40`) bit dominates any combo it appears in**, dropping the desk
  into the alarm/settings menu regardless of what is held with it.
- **`A + M` (`0x60`) is the one combo with a distinct function:** it enters a
  settings/parameter display (see [The `012` display](#the-012-display)).

Payload bit `0x80` of byte 1 and bits `0x02`..`0x80` of byte 2 are unmapped and
undocumented. **Reset/calibration on these desks is a physical gesture** (hold
Down at the low limit), not a serial opcode — no reset command exists in the
type-`0x02` space across any referenced research or any combo observed here.

## Display frames (type `0x12`)

Height and menu text are decoded from `9B 07 12 <d0> <d1> <d2> <crc> <crc> 9D`,
where `<d0..d2>` are the three 7-segment digit-cell bytes, using this font:

```
 aaa       a=0x01
f   b      b=0x02  c=0x04
f   b      d=0x08  e=0x10
 ggg       f=0x20  g=0x40
e   c      dp=0x80
e   c
 ddd
```

Glyphs decode via the table above; e.g. `0x3F`->`0`, `0x06`->`1`, `0x5B`->`2`,
`0x77`->`A`, `0x6D`->`S`/`5`, `0x50`->`r`, `0x40`->`-`, `0x09`->`:`. The decimal
point is bit `0x80` on a digit byte. `S` vs `5` (shared byte `0x6D`) is
disambiguated by context (an alphabetic neighbour or a `S-` set prompt forces
`S`).

Worked example — the height `72.4` is frame `9B 07 12 07 DB 66 A3 FF 9D`:
`07`->`7`, `DB`->`2.` (2 + decimal point), `66`->`4` = `72.4`.

### The `012` display

Holding **A + M** (`0x60`) puts the desk into a display showing a steady `012`.
Confirmed properties:

- **It is a genuine control-box `0x12` display frame**, not noise and not
  generated by the ESP firmware — the height/display decode path only publishes
  from a real `0x12` frame, and it fired for `012`.
- Decoded byte sequence: `9B 07 12 3F 06 5B <crc> <crc> 9D` (`3F`->`0`,
  `06`->`1`, `5B`->`2`).
- The display is **steady** while held (not the blinking alternation of the
  alarm-timer menu), and the desk **self-exits** back to the height readout a
  few seconds after release.
- It is almost certainly a **settings/parameter code** (on LoctekMotion CB-series
  boxes a Memory-key combo is the documented entry into the units/height-limit
  settings menu). **The exact meaning of the value `012` is unknown** and is not
  determinable from the serial line alone — it would require LoctekMotion service
  documentation, which is not public.
- **Reproducibility caveat:** `012` did not latch on every A+M attempt. Reliable
  entry required the display to be **awake first** (see [Wake behaviour](#wake-behaviour)),
  then A+M held firmly for ~4 s. Treat it as intermittent.

> Nothing is written or changed by entering this display; it is read-only and
> modifies no desk configuration.

## Wake behaviour

The serial **`00 00` heartbeat does NOT wake a sleeping display.** On this
CB38M2A-1, an idle/sleeping panel only wakes on a real key event (Up/Down/preset).
Any host driving this box programmatically must send an actual key command, not
the bare `00 00` wake/heartbeat, to bring the panel up. The `screen_wake_pin`
(GPIO14 / PIN20) hardware line remains the reliable wake path in this config.

## Status frames (`0x11` / `0x15`)

`0x11` and `0x15` arrive as a tight repeating **pair** (`0x15` then `0x11`),
roughly every 0.5–1.5 s, and **only while a key is held or a menu is active** —
they stop when the desk is fully idle. Both carry a constant single-byte payload
(`0x11`->`0x7C`, `0x15`->`0xBF`). They behave as **keep-alive / acknowledgement
frames the control box emits while it is receiving commands**, not as state data.
This corrects the earlier community assumption that these frames carry no payload:
they do carry a (constant) payload byte. `0x13` was never observed, including
during real motor travel, so it is not a motion-state frame on this box.

## Alarm safety

`0x01`/`0x02` are **native motor commands**. They only double as menu navigation
*while the alarm number is actively blinking (EDIT mode)*. If the menu times out
mid-sequence, a stray Up/Down drives the motor and the desk moves. This config
guards every alarm-adjust tap with three interlocks:

1. `alarm_editing == true` (the digit is provably blinking — real edit mode),
2. a fresh menu frame seen within 450 ms (`alarm_menu_ms` lockout),
3. desk height unchanged since the sequence started (instant abort on any motion).

The `set_alarm` script also chooses its step **direction once** by shortest
circular distance on the 1..99 ring, so it wraps correctly (e.g. 2 -> 98 goes
*down* 2,1,99,98 = 4 taps, not up 96) and never oscillates at the 99<->1 boundary.
Turning the alarm **off** uses a long `0x40` hold (~4 s), the same command as the
physical Alarm Hold.

## References

Protocol details were reverse-engineered against the physical desk and
cross-checked against the following prior work. The frame structure
(`9B … 9D`, length + type byte, CRC16/MODBUS) and the two-byte button payload
(including the `00 01` "Preset 4 / sit" command with no physical key) are
corroborated across all of these independent sources.

- **iMicknl / LoctekMotion_IoT** — the canonical community project (ESPHome
  packages, pin-outs, command list, height/7-segment decoding).
  <https://github.com/iMicknl/LoctekMotion_IoT>
- **nv1t / standing-desk-interceptor** — frame-structure reverse engineering:
  `<len>`/`<type>` bytes, CRC16/MODBUS over length+type+payload, message types
  `0x02` (button), `0x12` (height), and the `0x11` / `0x13` / `0x15` status frames.
  <https://github.com/nv1t/standing-desk-interceptor>
- **VinzSpring / LoctekReverseengineering** — Python packet parser and
  7-segment (`TM1650`) decode table used to confirm the display-glyph mapping.
  <https://github.com/VinzSpring/LoctekReverseengineering>
- **Dude88 / loctek_IOT_box** — Arduino control implementation (Alexa/MQTT),
  independent confirmation of the button command bytes.
  <https://github.com/Dude88/loctek_IOT_box>
- **grssmnn / ha-flexispot-standing-desk** — MicroPython/MQTT integration,
  additional command-byte confirmation.
  <https://github.com/grssmnn/ha-flexispot-standing-desk>
- **minifloat, mikrocontroller.net thread** — original 7-segment height decoding
  research that the above projects build on.
  <https://www.mikrocontroller.net/topic/493524>

## Findings unique to this build

Not present in the sources above:

- The `40 00` **Alarm (A)** key on this panel variant, and its tap-vs-hold
  semantics (tap = set-mode, ~4 s hold = alarm off).
- Closed-loop alarm decoding off the display frames.
- Live verification that held key combos (including a three-key combo `0x61`)
  OR their bits into one frame, and that **preset/memory combinations are no-ops**
  while `A`-bearing combos enter the alarm/settings menu.
- The **`A + M` -> `012`** settings display and its exact byte sequence.
- `0x11` / `0x15` identified as a keep-alive **pair** with constant payload bytes
  (`0x7C` / `0xBF`); `0x13` absent on this box.
- The **`00 00` heartbeat does not wake** a sleeping panel.
